# Release checklist

This checklist is for a practice preparing a controlled release candidate from this beta reference implementation. It does not make the repository a production compliance package. It records the engineering evidence that must exist before a practice can make its own go/no-go decision.

## Release naming

Use a release-candidate branch and tag that make the beta status plain:

```text
branch: release/v0.1.0-beta.1
tag:    v0.1.0-beta.1
```

Do not create a tag until every required gate below is complete and the repository is clean.

## Artefacts

A release candidate should have these artefacts:

- the tracked source tree at the release tag;
- a rendered managed settings file for the deploying practice, usually `dist/managed-settings.production.json`;
- the managed hook at the platform path referenced by that rendered file;
- the `skills/ai-policy-compliance/` directory installed beside the managed settings file;
- recorded output from the validation commands below;
- a rollback copy of the previous known-good managed-policy bundle;
- a release manifest (`dist/release-manifest.json`) containing hashes of all critical artefacts, signed by the deployment process outside this repository.

The rendered production settings file must not be committed. It contains firm-specific deployment values.

## Release manifest

The manifest schema (JSON) per design §5.3:

```json
{
  "$schema": "https://json.schemastore.org/claude-code-bundle.json",
  "type": "object",
  "required": ["commit_sha", "tree_state", "generated_at", "claude_code_version"],
  "properties": {
    "commit_sha": { "type": "string", "pattern": "^[a-f0-9]{40}$" },
    "tree_state": { "type": "string", "enum": ["clean", "dirty"] },
    "generated_at": { "type": "string", "format": "date-time" },
    "claude_code_version": { "type": "string", "pattern": "^\\d+\\.\\d+\\.\\d+" },
    "hook_hash": { "type": "string", "pattern": "^[a-f0-9]{64}$" },
    "settings_template_hash": { "type": "string", "pattern": "^[a-f0-9]{64}$" },
    "production_settings_hash": { "type": "string", "pattern": "^[a-f0-9]{64}$" },
    "sandbox_policy_hash": { "type": "string", "pattern": "^[a-f0-9]{64}$" },
    "compliance_skill_hash": { "type": "string", "pattern": "^[a-f0-9]{64}$" },
    "dependency_lock_hash": { "type": "string", "pattern": "^[a-f0-9]{64}$" },
    "minimum_version": { "type": "string" },
    "maximum_version": { "type": "string" }
  }
}
```

The sandbox policy and manifest are generated by:

```bash
python3 scripts/generate-matter-sandbox.py \
  --matter-definition dist/matter-definition.json \
  --output dist/sandbox-policy.json

python3 scripts/generate-release-manifest.py \
  --output dist/release-manifest.json \
  --production-settings dist/managed-settings.production.json \
  --sandbox-policy dist/sandbox-policy.json
```

The manifest records hashes. Signing the manifest, verifying the signature and installing the bundle are deployment responsibilities outside this repository.

## Required automated validation

Run from a clean checkout before tagging:

```bash
node tests/matter-guard.test.js
node tests/generate-matter-sandbox.test.js
node tests/render-production-settings.test.js
node tests/preflight-validate.test.js
node tests/generate-release-manifest.test.js
node tests/scan-docx-xml.test.js
node tests/compliance-evaluation.test.js
node tests/records-schema.test.js
node tests/docs-control-claims.test.js
node tests/scan-history.test.js
python3 scripts/check-clause-refs.py
python3 scripts/scan-history.py
python3 scripts/scan-docx-xml.py
python3 scripts/preflight-validate.py --mode template managed-settings.json
```

Regenerate policy Markdown into temporary files and confirm there is no drift from the authoritative DOCX files:

```bash
for d in ai-policy-legal-practice-template ai-protocol-barristers-chambers; do
  python3 scripts/docx-to-md.py "$d.docx" "/tmp/$d.regen.md"
  diff -u "$d.md" "/tmp/$d.regen.md"
done
```

Generate the deploying matter's sandbox policy, render the deploying practice's settings and validate production preconditions:

```bash
python3 scripts/generate-matter-sandbox.py \
  --matter-definition dist/matter-definition.json \
  --output dist/sandbox-policy.json

python3 scripts/render-production-settings.py \
  --firm-name "<practice name>" \
  --org-uuid "<Claude org UUID>" \
  --matter-roots "<absolute matter root>[;<alias>]" \
  --otel-endpoint "https://<collector>/v1/traces" \
  --sandbox-policy dist/sandbox-policy.json

python3 scripts/preflight-validate.py --mode production dist/managed-settings.production.json
```

Generate and verify the release manifest:

```bash
python3 scripts/generate-release-manifest.py \
  --output dist/release-manifest.json \
  --production-settings dist/managed-settings.production.json \
  --sandbox-policy dist/sandbox-policy.json

# If the working tree is dirty and the deployment process deliberately accepts that state:
#   python3 scripts/generate-release-manifest.py --allow-dirty ...

python3 scripts/generate-release-manifest.py \
  --verify \
  --output dist/release-manifest.json \
  --production-settings dist/managed-settings.production.json \
  --sandbox-policy dist/sandbox-policy.json
```

If the practice deliberately disables telemetry, record the reason and render with the explicit telemetry-disabled option provided by the renderer. Production preflight will warn that the record gap must be addressed in the practice's own Schedules 1 and 8.

## Version compatibility process (CFG-07)

The template and rendered production settings must record a certified version range:

```json
"requiredMinimumVersion": "2.1.219",
"requiredMaximumVersion": "2.1.300"
```

The maximum version is temporary and must be reviewed before promotion. The upgrade procedure:

1. Test the current and next candidate Claude Code version (N and N+1) against the compatibility suite.
2. Verify the tool registry completeness against the new version.
3. Verify settings schema compatibility.
4. Update `requiredMinimumVersion` and `requiredMaximumVersion` in the template.
5. Generate a new release manifest with the updated version range.
6. Publish the new bundle and manifest.

A new Claude Code version must not enter production until its settings and complete tool inventory pass the compatibility suite.

## Required manual validation

These gates depend on the deployment environment and cannot be proven by public CI:

- `claude doctor` on one machine per supported platform, confirming the managed settings file loaded and no managed keys were stripped;
- `/status` in a real session, confirming managed settings and hooks are in force;
- `CLAUDE_E2E=1 node tests/e2e.test.js` on a signed-in Claude Code installation;
- a real cross-matter refusal smoke test using the rendered production settings;
- a sandbox availability check showing that Claude Code refuses to run unprotected when `sandbox.failIfUnavailable` is true;
- a `SessionEnd` transcript filing check showing the record lands under the correct matter `_ai-record` directory or the configured central archive;
- platform exclusion evidence confirming native Windows is not treated as hard matter isolation;
- manifest signature verification confirming the installed bundle matches the approved release.

Record the command output or artefact path for each gate in the release notes.


## Required checks and repository protection

Before a release branch is merged or tagged, the repository owner must confirm that branch protection for `main` requires these checks and controls:

- CI / matter-guard (`ubuntu-latest`, `macos-latest`, `windows-latest`);
- CI / settings and policy;
- CI / secret scan;
- code-owner review for changes to settings, hooks, skills, scripts, tests, workflows, schemas and policy documents;
- stale approvals dismissed when new commits are pushed;
- no force pushes; and
- no merge while a required check is failed, pending or absent.

GitHub secret scanning and push protection must also be enabled before any public release. The local scanners in this repository are a supplement, not a substitute for the platform protection.

## Supply-chain gates

- [ ] Python dependencies install with `pip install --require-hashes -r requirements-lock.txt`.
- [ ] `check-jsonschema` is installed from the hashed lock file.
- [ ] The cached settings schema hash matches `schemas/claude-code-settings.schema.json.sha256`.
- [ ] `python3 scripts/scan-history.py` passes against full git history.
- [ ] `python3 scripts/scan-docx-xml.py` passes against Office XML payloads.
- [ ] The unpinned Claude Code review workflow is absent, or any replacement is vendored, pinned and review-only.
- [ ] Dependabot is configured for reviewed action and Python dependency updates.
- [ ] CODEOWNERS covers control files.

## Compliance skill evaluation

- [ ] `node tests/compliance-evaluation.test.js` passes.
- [ ] Ordinary compliant chronology, summary and index work remains available.
- [ ] Affidavit, witness statement and character reference content generation is refused.
- [ ] Restricted information requires recorded approval before use.
- [ ] Client material is treated as untrusted data and embedded instructions do not override the policy.
- [ ] Citation verification language remains cautious and never says AI has verified an authority.

## Records handoff contract

- [ ] `node tests/records-schema.test.js` passes.
- [ ] `docs/records-schema.md` is current for the release bundle.
- [ ] The external records service owner confirms storage, encryption, retention, legal hold, deletion, access logging and alerting are implemented outside this repository.
- [ ] A synthetic SessionEnd archive success and a monitored failure have both been observed.

## Owner-dependent gates

The repository can prepare the evidence framework, but cannot close these gates without a responsible human owner:

- [ ] Expert-report policy decision recorded in `docs/policy-decisions/expert-report-rule.md` and aligned across the DOCX, generated Markdown, managed instruction and compliance skill.
- [ ] OAuth token management decision recorded in `docs/policy-decisions/oauth-token-management.md`; no long-lived token without approved exception and rotation plan.
- [ ] Supplier evidence register completed with source URLs, owner names, checked dates and next-review dates.
- [ ] Legal source register completed against authorised primary sources.
- [ ] Data-flow model observed and approved by privacy, security and records owners.

## Do not tag until

- [ ] Git status is clean.
- [ ] CI is green on Ubuntu, macOS and Windows.
- [ ] Policy Markdown parity is clean against both DOCX files.
- [ ] Clause and schedule reference validation passes.
- [ ] Full-history secret and identifying-detail scan passes.
- [ ] Template preflight mode passes against `managed-settings.json`.
- [ ] Production preflight mode passes against the rendered settings file.
- [ ] Release manifest is generated and verified.
- [ ] Live E2E has passed on a signed-in Claude Code installation.
- [ ] OS sandbox availability and fail-closed behaviour have been checked in the target environment.
- [ ] The hook installed path matches the command in the rendered settings file.
- [ ] Transcript filing has been checked.
- [ ] Manifest signature verification has been checked.
- [ ] Independent security review is complete, or a responsible principal has expressly waived it for an internal beta only.
- [ ] The expert-report mismatch has been resolved or expressly accepted as a documented policy decision by the adopting practice.
- [ ] The deployment owner and rollback owner are named.
- [ ] The version compatibility range has been reviewed and updated.

## Installation check

Install the managed bundle to the platform's managed-policy directory:

```text
macOS         /Library/Application Support/ClaudeCode/managed-settings.json
Linux, WSL    /etc/claude-code/managed-settings.json
```

Install the hook and skill beside it:

```text
<system directory>/hooks/matter-guard.js
<system directory>/skills/ai-policy-compliance/SKILL.md
```

The hook command in the rendered settings file is literal JSON. It must match the installed path for the platform. A Linux path in a macOS deployment is a broken guard, not a portability feature.

Native Windows is not a production hard-isolation target for confidential Bash use. Use Windows with Claude Code inside WSL2 if the boundary needs to hold.

## Rollback

Before rollout, keep a copy of the previous known-good managed-policy bundle:

```text
managed-settings.json
hooks/matter-guard.js
skills/ai-policy-compliance/SKILL.md
release-manifest.json
```

Rollback procedure:

1. Stop new Claude Code sessions.
2. Replace the managed settings, hook, skill and manifest with the previous known-good bundle.
3. Run `claude doctor` on one machine per supported platform.
4. Start a new real session and check `/status`.
5. Run `node tests/matter-guard.test.js` against the rollback hook source.
6. Run a cross-matter refusal smoke test in a real session.
7. Verify the manifest signature.
8. Record the rollback time, machine, operator, reason and verification output.

Rollback verification succeeds only when a new session loads the previous settings, the hook path is valid, cross-matter refusal works in a real session, and the manifest signature verifies.

## Remaining caveats

A release tag proves only that these repository gates passed at that revision. It does not prove that a practice has satisfied its professional obligations, that the operating system sandbox actually worked on every target machine, or that the deployment remains correct after Claude Code settings change. Re-check after every Claude Code upgrade and before adding any built-in, plugin or MCP tool surface.
